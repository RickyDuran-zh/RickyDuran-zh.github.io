ubuntu18.04.4如何vibecoding?

概述

起因在于楼主这段时间在用 IMX6ULL 开发板做项目，受限于交叉编译工具链的版本，VMware 安装了 Ubuntu18.04.4 的版本。系统版本比较老，vscode 没有 claude 的插件支持，要在命令行安装 claude 的话，可能装个 node.js 或者 npm 都费劲；codex 的话也没有去进行尝试配置。总之一直没找到合适的方法，此前一直是 codex 给我压缩包，我再把压缩包 scp 到虚拟机或者手动 CV，效率之低下，可想而知。最近想到了一个曲线救国的方法可以比较好的实现所谓”vibecoding”的理念。

流程

整体工作流

大致工作流的话，楼主 vibecoding 用的是 Claudecode + Deepseek V4 pro + CC-switch(具体配置非常简单，网上一搜就有一堆)的方式。刚好今天 Deepseek V4 pro 的 TOKEN 费用永久2.5折，这边还是支持一下国产大模型。
宿主机这一侧主要就是去 vibecoding，实现一些驱动，UI 的编写，以及修改设备树。编译以及板卡部署还是在虚拟机里面去完成。
原理的话也是比较简单，宿主机和虚拟机中都有项目文件夹，区别在于宿主机这边不放完整的内核源码，只准备一个文件夹 dts 放 IMX6ULL 适配的设备树 imx6ull-mmc-npi.dts，然后通过一个 sync_to_vm.sh 的同步脚本把新增或者改动的代码全部覆盖到虚拟机中，然后在 CLAUDE.md 文件中给 CC 说清楚限制和规定就行了。
每次日常开发完调用一次 ./scripts/sync_to_vm.sh 即可实现代码的同步。

同步脚本

通过 SSH 通道 + tar 流式传输实现代码同步，通过 exclude 去过滤掉不需要的文件，DTS 单独同步。

效果

可以实现”vibecoding for embedded”的闭环。其实编译也可以让 agent 去干，但这一部分由于要在板子上部署，工具链版本还是比较严苛的。让 agent 进入虚拟机进行交叉编译理论上可行，但是不是很放心，可以仅仅让 agent 去写 Makefile，至于编译还是得自己把关(高风险操作还是不要交给 agent 了)。
