音视频业务basic understandings

概述

第二个项目将在 RK3588 的基础上开发多路视频智能分析的中间件，这篇博客按一条视频从采集到播放的完整链路，把音视频基础知识分层梳理一遍：像素 → 编码 → 封装 → 时间戳 → 协议 → 硬件。

1、全局地图：一条视频的旅程

我们项目的实际链路是中间一段：MP4/RTSP -> FFmpeg 解复用 -> h264_mp4toannexb（需要时）-> MPP 硬解码出 NV12 -> 转 BGR -> RKNN 推理叠框 -> 2×2 拼接 -> 转 I420 -> MPP 硬编码 -> FFmpeg 封 FLV -> RTMP 发送。

遇到问题先判断它属于哪一层：像素格式、编码、容器、传输协议、硬件缓冲区，还是业务推理，不同层的名词不能混用。比如”MP4 解码器”这种说法就不准确——先由 demuxer 解析 MP4 容器取出码流，再由 H.264 decoder 解码。

2、原始图像：帧、像素格式与内存布局

Frame - 视频是一系列按时间显示的静态图像，每一张就是一个 frame。一帧除了像素，还应携带宽高、像素格式、每个平面的地址和 stride、PTS 或采集时间戳、缓冲区所有权——只传一个 void* data，接收方既不知道如何解释这块内存，也不知道它被用到什么时候才安全。

FPS - 链路上不止一个值：采集、解码、推理、合成、编码、播放各有一个，且可以不同。比如采集 25 fps、每两帧推理一次，推理只有 12.5 fps，但每帧复用最近一次检测结果，输出仍是 25 fps。

2.1 RGB 与 YUV

YUV/YCbCr - 指亮度参量和色度参量分开表示的像素格式。利用了人眼对亮度敏感、对颜色不敏感的特征，对色度降采样来省数据：4:4:4 不降采样；4:2:2 水平方向每两个 Y 共用一组 UV；4:2:0 水平垂直都降采样，2×2 的 Y 共享一组 UV。一个为了显示和处理（RGB），一个为了传输和存储（YUV），视频编解码硬件通常也更偏好 YUV。

数据量感受一下：1920×1080 的 BGR8 一帧 = 1920×1080×3 ≈ 5.93 MiB，25 fps 光遍历一次就是约 148 MiB/s；换成 8bit 4:2:0，每像素平均 1.5 byte，一帧只有约 2.97 MiB。

颜色矩阵与范围 - RGB↔YUV 的转换不止一套公式：矩阵有 BT.601（SD）、BT.709（HD）、BT.2020（UHD/HDR）；范围有 Full range（0255）和 Limited/TV range（亮度 16235、色度 16~240）。矩阵或范围用错会发灰、黑位不对、偏色，不能只看格式名叫 NV12 就推断它们。

2.2 内存布局与 Stride

I420/YUV420P - Y + U + V 三平面，U 在 V 前。
YV12 - Y + V + U，和 I420 只是 UV 顺序相反。
NV12 - Y 平面 + UVUV 交错的第二平面（semi-planar），Rockchip 等视频硬件最常见。
NV21 - Y + VUVU，色度顺序与 NV12 相反。

把 NV12 当成 NV21 会明显偏色，当成 I420 则连平面结构都解释错了。我们项目 MPP 解码输出按 NV12 处理，编码前准备 I420，中间为了 OpenCV 绘图和模型输入转 BGR。

Stride - 可见像素宽度之外的行跨度。硬件常要求 16、64 字节对齐，可见宽度 1920 时 stride 可能是 1936、1984 或 2048，缓冲区高度同理。直接假设 stride == width 会得到斜屏、颜色错位或边缘绿条；NV12 的 UV 平面起点也要按 stride × height_stride 算，而不是 width × height。

3、编码与解码：从原始帧到码流

1080p 4:2:0 一帧约 3 MiB，25 fps 一路就是每秒 70+ MiB，存储和网络都扛不住，所以要压缩。

3.1 宏块与帧类型

宏块 - 视频编码处理的基本单元，通常由一个 16×16 亮度像素块和附加的一个 8×8 Cb、一个 8×8 Cr 彩色像素块组成（H.265 改用 8×8 到 64×64 可变大小的 CTU）。

I 帧 - 帧内编码帧，完整的独立画面，不依赖其他帧就能解码显示。帧内压缩仅考虑本帧数据，压缩率一般不高。
P 帧 - 前向预测帧，只记录变化部分，需要参考前面的 I/P 帧。
B 帧 - 双向预测帧，参考前后的帧，压缩率最高，但会引入解码重排序。
IDR - H.264/H.265 中的关键随机访问点，解码器从这里重新开始，不依赖 IDR 之前的参考图像。

3.2 GOP

GOP（Group of Pictures）- 实质就是两个 I 帧的间隔。码率不变时 GOP 越大 P/B 帧越多、画质相对越好，但首屏、跳转、丢包恢复变慢；GOP 短则反过来。实时监控常设 1~2 秒一个关键帧，我们项目当前用 gop = fps。

3.3 码率控制

码率是每秒产生的压缩数据量（kbps），设定应高于该分辨率的最低码率要求、低于网络带宽，不是越大越好。

CBR - 固定码率，码率基本恒定并接近目标值，利于带宽规划。
VBR - 动态码率，按画面复杂度调整，简单部分小码率、复杂部分大码率。参数：MaxBitrate、ChangePos、MaxQp、MinQp。
AVBR - 平均可变码率，VBR 的一种，适合静止/动态画面频繁切换的场景，多一个 MinStillPercent 参数。

QP - 量化参数，直接控制量化步长。QP 每增加 6，量化步长翻倍，细节损失越多、码率越低；MinQp/MaxQp 分别限制最好和最差的画质，对应静止和运动画面。

Profile - 编码工具集合：66 Baseline 只支持 I/P 帧、无交错；77 Main 增加 B 帧和交错；100 High 再加 8×8 预测和自定义量化。同画质下更复杂的工具压得更小。
Level - 解码复杂度上限（宏块处理率、分辨率、码率）。设太高旧设备解不动，与实际内容不符播放器可能直接拒绝。

3.4 码流结构：NAL

H.264 - 原始码流（ES）不含任何封装信息，由 NAL 单元组成，每个 NALU 是一个基本编码单元。结构上是 VCL（承载编码数据）+ 非 VCL（参数集、SEI 等补充信息）；NAL 的 payload 是 RBSP，即去除字节填充、加上终止位后的实际编码数据。

SPS/PPS - 解码必需的参数集，描述分辨率、profile、level、参考帧数等（H.265 多一个 VPS）。推流或封装时缺失、格式不符，播放器黑屏或只能从后续关键帧开始。

Annex B 与 AVCC - NAL 边界的两种表达。Annex B 用 start code（00 00 01 / 00 00 00 01）分隔，参数集穿插在码流里，裸流和 TS 常见；MP4/MOV 用长度前缀，参数集放在容器的 extradata 里。很多硬件解码器更适合 Annex B，FFmpeg 提供 bsf h264_mp4toannexb / hevc_mp4toannexb 做转换——bsf 只改码流组织，不做像素级重编码，开销远小于转码。

4、封装：Container、Demux 与 Mux

容器 - 把一路或多路音视频流、字幕、元数据组织在一起。容器扩展名不是编码格式，.mp4 里可以装 H.264、H.265、AAC。

TS 流 / PS 流 - 传输流/节目流，复合流的一种（一条流里同时包含视频和音频）。ES 是编码后的裸流（H.264、AAC），没有时间信息；编码器把 ES 拆成 packet 并加包头，附上 PTS（显示时间戳）和 DTS（解码时间戳），得到 PES；TS/PS 再把视频、音频的 PES 复用成一条流。

FLV - Adobe 推出的网络流媒体封装，与 RTMP/HTTP-FLV 结合紧密，结构 = Header + Tag（video tag / audio tag / script tag）。

Demux - 从容器里取出压缩 packet，FFmpeg 里由 libavformat 负责：avformat_open_input 打开输入 -> avformat_find_stream_info 探测流 -> av_read_frame 逐个读 packet。注意 av_read_frame 名字叫 frame，返回的其实是压缩 packet。

Mux - 反向操作，把编码后的 packet 按容器规则写出。推流端流程：alloc_output_context2 -> new_stream -> 填 codec 参数和 extradata -> avio_open 连接 RTMP -> write_header -> 循环 av_interleaved_write_frame -> write_trailer。Mux 不等于编码，我们项目编码由 MPP 完成，FFmpeg 只管封装和协议 I/O。

5、时间戳与音视频同步

Packet 与 Frame - packet 是压缩数据单元，frame 是解码后的原始数据。一个 packet 不保证正好出一个 frame：可能暂时不出帧、出多帧，或一帧跨多个 packet，所以不能用”每读一个 packet sleep 一次”控制播放速度——本地文件播放过快多半就是这个原因。

PTS/DTS - PTS 是显示时间戳，DTS 是解码时间戳。没有 B 帧时两者相同，有 B 帧时解码顺序 ≠ 显示顺序。

Time base - 时间戳不是天然以秒为单位：time_base = 1/90000 时，PTS 加 90000 才是一秒，seconds = pts × num / den。FFmpeg 用 av_packet_rescale_ts 做时基转换，比手写浮点安全。我们当前版本丢弃了输入原始时间戳、用递增帧号生成 PTS，只适用于固定帧率、无 B 帧的初始版本，接入实时流后必须重建统一的媒体时间轴。

时钟域 - 测耗时和延迟用单调时钟 steady_clock，system_clock 会受校时影响；多摄同步前先确认各摄像头的时间戳是否来自同一时钟域。

PCM - 未压缩的音频采样。比特率 = 采样率 × 位深 × 通道数，双声道 48kHz 16bit = 1,536,000 bit/s。内存布局分 Packed（LRLRLR 交错）和 Planar（LLL + RRR），FFmpeg 格式名后缀 P 表示 planar，如 FLTP。
WAV - 不是编码格式，本质是 PCM 裸数据外面套了个文件头。
AAC - 取代 MP3 的新一代音频编码，更高压缩率、更高品质、更低解码开销，MP4/FLV/RTMP 生态标配。两种形式：ADIF 能确定音频数据的开始位置，适合文件；ADTS 每帧都带头部（fixed + variable + 裸流 ES），适合流式。

A/V Sync - 音频和视频要映射到同一播放时间轴，不能谁先到就发谁，通常由音频时钟、视频 PTS 或统一的 master clock 驱动，配合丢帧、补帧或重采样策略。

6、流媒体协议

RTSP - 实时流传输协议，控制用，类似遥控器只下命令不传视频，常见动作 OPTIONS/DESCRIBE/SETUP/PLAY/TEARDOWN。
RTP - 实时传输协议，基于 UDP，媒体数据由它承载，带 sequence number 和 timestamp，本身通常不重传；NAL 太大会被拆成多个 RTP 包。
RTCP - RTP 控制协议，周期性发送丢包率、延迟、抖动等质量报告，接收端据此动态调整码率或 FEC 强度。
SDP - 会话描述协议，RTSP DESCRIBE 的响应就是它，描述媒体类型、codec、payload type、时钟率。
SIP - 会话初始协议。GB/T 28181 - 公共安全视频监控联网标准，SIP 控制 + RTP 传输。

RTSP 的媒体传输可以走 UDP（延迟低、丢包不阻塞，但防火墙和网络设备处理麻烦），或 TCP interleaved（RTP/RTCP 复用在 RTSP 的 TCP 连接上，穿透容易且可靠，但丢包重传会累积延迟）。我们当前偏向 rtsp_transport=tcp 先保证连通。

RTMP - 基于 TCP 的实时消息协议，传统直播链路用 FLV 标签承载 H.264/AAC。URL 结构 rtmp://host:port/app/stream-key；浏览器不能直接播放，需要服务器转 HLS/WebRTC。其他协议定位：HLS 是 HTTP 分片，分发友好但延迟较高；WebRTC 交互式低延迟但协议栈复杂；SRT 面向不稳定公网。选协议看延迟、网络、客户端和安全需求，不因为名字流行就加接口。

7、RK3588 平台组件

MPP - Media Process Platform，Rockchip 的硬件编解码库，屏蔽不同芯片的硬件差异，提供统一的视频编解码接口，我们用它做 H.264/H.265 硬解和 H.264 硬编码。MPP 输出的是带对齐 stride 的硬件 buffer，高性能做法是保留 MppBuffer/DMABUF 身份直接传下游，而不是立刻逐行 memcpy 到普通内存。

RGA - 独立的 2D 硬件加速器，做 resize、crop、rotate、颜色转换、blit，正好覆盖 NV12↔RGB 这类活。硬件失败时可以回退 OpenCV，但要计数并告警，否则性能退化会被掩盖。

RKNN - Rockchip 的 AI 推理引擎和模型格式，.rknn 模型跑在 NPU 上。要关心输入布局（NCHW/NHWC）、量化参数（zero point/scale）、core mask 绑核，输入预处理必须和模型转换时一致。多模型并行不保证线性加速，NPU 核、DDR 带宽、RGA、CPU 后处理都可能成为瓶颈。

DMA-BUF - 用 fd 表示可跨设备共享的缓冲区，理想链路是 ISP、RGA、NPU、编码器共享同一块底层内存。但有 fd 不等于零拷贝：各模块要支持导入导出、格式和 stride 兼容、cache 同步正确、buffer 生命周期覆盖所有使用者。我们目前属于”用了硬件加速但不是零拷贝”——解码缓冲区逐行 memcpy、BGR 帧 clone 多次、编码前再 memcpy 进 MPP，优化顺序是先建立逐阶段耗时基线，再消重复拷贝和前处理，最后尝试 RKNN tensor memory 和 MPP 输入共享。

Cache coherency - CPU 和硬件同时访问 DMA buffer 时要做 cache sync，漏了会偶发旧数据、花屏，且只在高负载下复现。

8、MIPI 摄像头链路

Sensor 把光变成数字信号，驱动要管 I2C 寄存器、输入时钟、电源 regulator、reset/pwdn GPIO 和曝光增益等 controls。很多 sensor 输出 RAW Bayer（RGGB 等排列，每个像素只采到一个颜色分量），经过 MIPI CSI-2（数据协议，底层是 D-PHY 物理层）送到 ISP 做 demosaic、降噪、AE/AWB、gamma、lens shading，最后输出 YUV。RAW10/12 指有效位深，内存里的 packing 方式要另查，不能当 16bit 灰度图。

应用侧通过 V4L2 拿帧：枚举格式 -> 设置 format/fps -> 请求 buffer（mmap 或 DMABUF）-> STREAMON -> DQBUF/QBUF 循环。media controller 用 graph 描述 sensor、CSI、ISP 之间的拓扑：

接入前先用 v4l2-ctl 稳定抓帧，再接应用，否则应用层日志会把驱动问题复杂化。另外先确认拿到的是 RAW 还是 ISP 后的 NV12——已经是 NV12 就没必要”先编码再解码”绕一圈。

9、推理前处理与后处理

Letterbox - 直接 resize 到模型输入尺寸会拉伸目标形状；letterbox 保持长宽比再 pad 补齐：scale = min(Mw/W, Mh/H)，pad_x = (Mw − W×scale)/2。后处理还原坐标时必须先减 padding 再除 scale，顺序反了框就偏移。

NCHW/NHWC 与量化 - 内存布局必须和 RKNN tensor attr 一致，shape 数字相同不代表布局正确。INT8 非对称量化：real = (q − zero_point) × scale，后处理要按每个 tensor 的 zp/scale 反量化。

IoU/IoM/NMS - IoU 是交集/并集，IoM 是交集/较小框面积（适合大框包含小框），NMS 按置信度保留框、抑制重叠过高的框。业务上注意框的语义：全身框和头部框大小差异天然很大，IoU 可能很低而 IoM 更合适；比把两种框合并更合理的，常是建立 helmet belongs_to person 这类关系。

多模型调度 - 每路一个 context / 多路共享串行 / 绑不同 NPU core / 同模型多 context 并发，选哪种先测模型耗时和 NPU 利用率——线程池提交了任务，不代表 NPU 真的在并行。

10、实时链路思维

吞吐与延迟 - 吞吐是每秒处理多少帧，延迟是一帧从输入到输出走多久。吞吐高不代表延迟低：队列积压 100 帧的系统照样 25 fps 输出，但你看到的是 4 秒前的画面。给每帧各阶段打时间戳、统计 P50/P95/P99，延迟问题才能定位到阶段。

背压 - 下游慢于上游时必须选策略：阻塞上游（不丢帧但延迟涨）、丢最新帧（保留历史，适合离线）、丢最旧帧（优先最新画面，适合实时监控）、按关键帧/事件保留。我们推流队列有上限并丢最旧帧，其他阶段也要统一规则。

内存所有权 - cv::Mat 赋值只加引用计数，clone() 才复制像素；跨线程要明确上游会不会复用缓冲区，从 MPP/DMA 内存构造的 Mat 引用计数延长不了硬件 buffer 的生命周期。每个队列都要有容量上限和满队策略——无界队列在网络断开或模型变慢时，表现得就像内存泄漏。
